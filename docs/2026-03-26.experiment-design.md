## RAG Architecture

### Embedding

- **Model:** `gemini-embedding-001` (3072 dimensions)
- **Vector store:** Vertex AI Vector Search (only)
- **Query time:** strip Python comments → embed full source → vector search

### Ingest Strategy

| Collection | Text embedded into Vertex AI | Why |
|---|---|---|
| `grammar_mappings` | `python_pattern` only | Query is Python source → match on Python side |
| `parallel_corpus` | Python code side only | Same — find similar Python code |
| `api_mappings` | `python_api` only | Same — match Python API usage |
| `go_docs` | `{description} Example: {example}` (Go text) | Queried with Go API names (see pipeline below), not Python source |

### Query Pipeline (per translation request)

```
1. strip_python_comments(source)           → stripped_source

2. [if A] grammar_mappings.query(stripped_source, k)
          → go_pattern + description per match

3. [if B] parallel_corpus.query(stripped_source, k)
          → python_code + go_code per match

4. [if C] api_mappings.query(stripped_source, k)
          → python_api + go_api + description per match
          → collect go_api names → go_api_query

5. [if C and D] go_docs.query(go_api_query, k)
          → api + description + example per match

6. Format all results → inject into LLM prompt
```

Step 4 → 5 is the bridge: Go API names from api_mappings are used as the query for go_docs. This means go_docs is only ever queried with Go terminology, which is what it is indexed on.

No tree-sitter grammar extraction at query time. `grammar_extractor.py` is no longer used in the retrieval path.
